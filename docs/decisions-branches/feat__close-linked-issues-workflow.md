## 2026-09-15 14:42 - reporulez#71 ask C: reusable workflow that closes linked issues on merge into dev

**Reasoning:** GitHub's Closes #N auto-close only fires on merge into the DEFAULT branch, so with everything targeting dev (reporulez#71's own convention), a merged PR's linked issue never auto-closes -- AGENTS.md convention 6 says close it by hand today ('with the PR + SHA'). bin/extract-closed-issues.sh parses the PR body for closing keywords (close/fix/resolve, all tenses) followed by #N, owner/repo#N, or a full issue URL, splitting same-repo from cross-repo references; bin/close-linked-issues.sh calls it and does the actual closing via gh, writing a GITHUB_STEP_SUMMARY-flavored markdown table. Both scripts are unit-tested offline: extraction against 22 PR-body fixtures (including 'only the reference directly after a keyword counts' and 'fenced code blocks are stripped, inline code spans are not'), closing against a stubbed gh (10 cases covering open/already-closed/permission-denied/dry-run/cross-repo). Two guards were mutation-tested by hand (neuter, confirm red, revert): the cross-repo-without-token failure path, and (in the sibling ask-B script) the examines-nothing guard.

**Alternatives considered:** Embed the closing logic as inline workflow YAML instead of a bin/ script -- rejected after a first draft: ~80 lines of loop/gh-call logic with no test coverage, for a mechanism that mutates real GitHub state (closes issues), was the wrong risk trade for a repo whose own convention is 'everything meaningful lives in bin/ + tests/'. Pulled it into bin/close-linked-issues.sh specifically so it could be tested against a stubbed gh before shipping. Auto-include a bare #N reference following a comma after a keyword-qualified one ("Closes #1, #2" closing both) -- rejected: GitHub's own linking does not chain a second bare reference into a close-trigger, and guessing intent beyond what GitHub itself would honor is exactly the kind of silent-widening this script should not do unilaterally. Assume GitHub's PR-body renderer autolinks inside single-backtick inline code spans and match through them -- rejected as an unverified claim; picked the conservative reading (does not count) since under-closing is recoverable by hand and over-closing on an unconfirmed rendering assumption is not (documented as an ASSUMPTION, not a citation, in the script's own header, matching this repo's established rhetorical convention from bin/validate-ruleset.sh).

**Implications:**
- Cross-repo issue references are NOT closed unless the calling repo's wrapper workflow supplies an optional cross-repo-token secret with issues:write on the target repo -- without one, every cross-repo reference found is reported NOT CLOSED in the job summary and fails the job (never a silent skip). Already-closed issues are a no-op, not a failure, and are not re-commented on, so a re-run of this workflow is idempotent. This job runs strictly after the PR has already merged, so failing it blocks nothing -- but it keeps the workflow run red and visible in the Actions tab, per the standing rule that a check finding nothing (or failing to act) must not read as a pass. Adoption is opt-in per repo (a 2-line wrapper workflow), same limitation as every other reporulez mechanism today.
