## 2026-09-15 14:29 - Add org-default-protection and org-staging presets, ensure-dev-branch.sh, and docs/branch-policy.md for reporulez#71's org-wide main=production/dev=staging policy

**Reasoning:** Live thrillmade org already runs a working 5-ruleset model (org-baseline+org-default-protection on main, org-staging on dev, plus two more org-level rulesets, CI must pass and no-delete-dev-main) but only org-baseline had a checked-in preset and apply-org.sh variant -- the other two were applied by hand, so the tool couldn't reproduce or audit them. A repo also needs a dev branch before org-staging protects anything there, which no existing script created.

**Alternatives considered:** Fold dev-branch creation into apply-org.sh itself, or make audit.sh's --include-ruleset check dev/default-branch too -- rejected both: apply-org.sh's job is POSTing an org ruleset in one API call, not per-repo branch mutation with per-repo failure modes; and audit.sh is documented read-only, so adding a mutating dev-branch-check duplicates ensure-dev-branch.sh's detection logic in a second place it can drift from.

**Implications:**
- Every org preset (org-baseline, org-default-protection, org-staging, and org-ci-must-pass for the live "CI must pass" ruleset) is re-captured from the live org rulesets, so applying any of them to today's org should change nothing. The one field not verified is the org rulesets' repository condition, which a repository-level read does not return: the presets say repository_name ~ALL, and an org owner's first dry run shows whether live agrees. org-staging's bypass actors are in pull_request mode, as live has them; bin/validate-ruleset.sh's admin-bypass-required check now accepts an admin bypass in always or pull_request mode. The fifth, no-delete-dev-main, now has a preset too (org-no-delete-dev-main): it carries no bypass actor and one rule, deletion, and admin-bypass-required now exempts a ruleset whose every rule is deletion, since such a ruleset blocks no commit, push or merge. Any other rule alongside, non_fast_forward included, and the check applies.
- bin/apply-org.sh is a dry run by default: it prints the difference between preset and live and writes only with --apply. --apply alone writes only a difference it can show is strictly tighter, or a create where no live ruleset is named like it (folding ASCII case, spaces, hyphens and underscores; look-alike characters from other scripts are not detected); anything else is weakening (fail closed, including any field it has no rule for, any key absent on one side or of another JSON type, and any added or widened bypass actor) and needs --allow-weakening, while removing or narrowing a live bypass needs the separate --allow-bypass-removal. It refuses a duplicate or near-duplicate name and a live read that failed or returned nothing usable, and exits only 0, 1 or 2. bin/ensure-dev-branch.sh is a dry run by default too, creates only with --apply where branches/dev is a 404, skips archived repos and forks, and exits non-zero on any failure. bin/audit.sh reports a failed or unusable read, and a field validation without a verdict (anything but exit 0, or exit 1 with a violation line), as "could not audit" and exits 2. tests/test-org-scripts.sh pins these against a fake gh that records every call.
- ensure-dev-branch.sh warns (never auto-fixes) when a repo's default branch isn't main, surfacing exactly the failure this audit found in one private repository, because flipping a default branch is a human decision this repo's own policy doc says so.

## 2026-11-12 21:58 - Org ruleset tooling reworked after four review rounds: presets re-captured from live, apply is a dry run that can only tighten, audit and validator never report clean when they did not check

**Reasoning:** The first version of this pull request would have changed production protection on a re-apply: the checked-in org presets no longer matched what is live, and apply replaced a ruleset by name with no diff. Live is the source of truth, so all five org rulesets are captured read-only as presets. Apply now compares field by field and writes, with --apply alone, only a change it can prove tightens; anything else, including a key that is merely absent or of another type, is refused unless --allow-weakening is given, and removing or narrowing a live bypass needs --allow-bypass-removal. An unusable read is a failed read. Audit reports could-not-audit unless the validator gave a real verdict, and the validator accepts exactly one JSON object.

**Alternatives considered:** Keep the presets as the source of truth and apply them (would strip three live bypass actors and loosen the staging ruleset). A short list of refused loosenings (the first rework; a reviewer got twelve weakenings through it). Exempting every ruleset without merge-gating rules from the admin-bypass check (only a well-formed deletion-only ruleset is exempt, the smallest change that lets the live delete-protection ruleset validate).

**Implications:**
- Nothing was applied to the organisation. The repository condition of the live org rulesets could not be read without the admin:org scope, so each preset carries repository_name ~ALL unverified; the first dry run by an org owner shows any difference before anything is written. This repository's own dependabot.yml now targets dev (its checker exits 1 before, 0 after; it takes effect after promotion). Known limits, stated in the scripts: the near-duplicate name check folds ASCII only; there is no precondition between the read and the write.
