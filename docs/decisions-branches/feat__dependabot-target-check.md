## 2026-09-15 14:31 - reporulez#71 ask B: check + reusable workflow that fails when a repo's dependabot.yml doesn't target dev

**Reasoning:** GitHub reads .github/dependabot.yml only from a repo's default branch and there is no org-level dependabot setting, so nothing org-wide stopped a repo's dependency-bump PRs from opening against main forever -- this already happened for real (clud-bug#328: main drifted 22 commits ahead of dev in 3 weeks, a 16-file conflict lane) and is still live today on reporulez's own default branch and on both thrillmade/clud-bug#340's and a private sibling repository's unmerged base state, used here as control-test fixtures. bin/check-dependabot-target.sh checks a file, a single repo (--repo, via gh api against the default branch), or a whole org (--all, mirroring bin/audit.sh's enumeration); the reusable workflow_call workflow lets any repo adopt it with a 2-line wrapper; it audits the default branch's config, so it catches a regression after it merges, not in the PR that introduces it. Exit-code taxonomy (0 clean / 1 real violation / 2 couldn't-even-check) mirrors bin/validate-ruleset.sh's, chosen specifically so 'examines nothing' (missing file, unparseable YAML, zero repos enumerated) can never read as exit 0 -- reporulez#71's own words for the recurring defect class. That guard was mutation-tested by hand (neutering the zero-repos die() and the no-updates early-exit, confirming the suite goes red both times, then reverting) rather than asserted.

**Alternatives considered:** Fold every --all-mode outcome (missing file, parse error, wrong target-branch) into a single exit-1 'violations found' bucket instead of aborting the whole org scan on the first bad repo -- rejected because bin/audit.sh's own precedent is to continue past a per-repo GET failure and report at the end, and an org-wide audit that dies on the first non-conformant repo out of dozens is far less useful than one that reports all of them. Treat a repo with NO dependabot.yml at all as a silent skip (not a violation) in --all mode -- rejected: reporulez#71 says explicitly that a check finding no dependabot.yml must not exit 0, and every templates/dependabot/*.yml this repo ships is something a managed repo is expected to install, so absence is itself worth surfacing, not hiding.

**Implications:**
- Fixing reporulez's own live-violating .github/dependabot.yml is NOT included in this change: PRs that edit dependabot.yml must target main directly (GitHub reads it only from the default branch), and this PR targets dev per reporulez#71's own ask -- that fix is a separate main-targeted follow-up, noted in tests/fixtures/dependabot/real-reporulez-missing-target.yml's header. Consuming repos must add a 2-line wrapper workflow to adopt the check (nothing forces adoption org-wide yet, same limitation AGENTS.md already documents for every other reporulez mechanism). The reusable workflow checks out its own source through the job context (job.workflow_repository at job.workflow_sha) rather than a hardcoded pin; github.workflow_ref is the caller's inside a called workflow and must not be used. A pass needs positive proof: the Python side must print one well-formed result line, and a crash, traceback or missing line is exit 2 (could not examine), as is a failed or partial --all listing.

## 2026-09-15 14:53 - fix: check_one's verdict never survived --all --quiet's subshell (clud-bug PR #73 review)

**Reasoning:** clud-bug's review of PR #73 (Wasp/opus, pass 2, found independently) caught a real, severe bug: check_one signaled its verdict via a global variable (CHECK_VERDICT) set from inside the function, but --all --quiet's call site wraps check_one in a command substitution (FINDINGS="$(check_one ...)"), which bash always runs in a subshell -- so the assignment made inside check_one never reached the parent shell. Reproduced live before fixing (two stubbed-gh runs): --all --quiet against an org where every repo was 100% compliant still exited 1, unconditionally, on every run; a mixed clean+bad run printed the CLEAN repo's line too, defeating --quiet's whole purpose. Root cause confirmed by a targeted mutation afterward: reintroducing the exact global-variable pattern flips two new regression tests red (added specifically because the original suite never exercised --all with more than zero repos, which is exactly why this shipped in the first PR).

**Alternatives considered:** Keep the global-variable convention and just remember not to wrap check_one in $(...) -- rejected: that's exactly the discipline that already failed once (the original code's own comment explicitly reasoned about set -e and subshells and still got it wrong for this call site). Fixed the class instead: check_one now returns its verdict via its own exit status (0 clean / 1 violation / 2 no-updates / 3 parse-error), which DOES survive $(...) correctly -- $? after x="$(f)" is f's real exit code regardless of what f assigned to variables inside the subshell -- so every call site uses the same 'cmd && rc=0 || rc=$?' idiom already established elsewhere in this file, with no special case for the wrapped-in-$() call site to get wrong again.

**Implications:**
- Also fixed the minor finding from the same review pass (fetch_repo_yaml conflated a genuine fetch failure with a successfully-fetched-but-empty dependabot.yml under the same empty-string signal -- both still correctly exited 2, but the error message misreported which one happened; now distinguished via the function's own exit status, same fix shape as the critical bug). Did NOT act on the review's third finding (actions/checkout@v7 'does not exist') -- verified false via gh api repos/actions/checkout/releases (v7.0.1 is real and current) and confirmed the same pin already ships unmodified in this repo's own pre-existing test.yml and check-doc-links.yml, neither touched by this PR.

## 2026-11-12 02:32 - Dependabot target check, after review: a pass needs positive proof, the reusable workflow checks out its own commit, and a private name is gone

**Reasoning:** A first independent review of this pull request found three things. The checker printed a green tick and exited 0 when its embedded parser crashed (an invalid date scalar, invalid UTF-8), which is the examined-nothing-reads-as-a-pass case it exists to prevent. The reusable workflow chose which ref of this repository to check out from github.workflow_ref, which inside a called workflow names the caller's file and ref, so a caller's pull request would have asked this repository for the caller's ref. And four added lines named a private repository in a public one.

**Alternatives considered:** Catch the two crashing inputs specifically: rejected, any other parser failure would still read as clean. Ask callers to pass the ref as an input: rejected, GitHub provides the called workflow's own repository and commit in the job context, measured at runtime with a throwaway workflow run. Add a self-check job to this repository's own CI: not yet, this repository's dependabot config has no target-branch on its default branch, so the job would be red on a true finding until that is fixed and promoted.

**Implications:**
- A config passes only when the parser prints exactly one result line, exits zero, and its counts agree with the violation lines; anything else is could-not-examine, exit 2. The --all mode treats a failed or partial listing the same way. The workflow checks out with job.workflow_repository and job.workflow_sha and fails before the checkout if either is empty. Inputs reach the shell through env. The description says the check reads the default branch's config, so it cannot block the pull request that introduces a regression. Known limit: NUL bytes in a config are dropped by the shell before parsing.
