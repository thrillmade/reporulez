## 2026-08-24 08:31 - reporulez#68: bin/validate-ruleset.sh -- validate a ruleset's required fields before it is ever applied

**Reasoning:** Nothing checked a ruleset's contents before POST/PUT -- only JSON syntax. An invalid ruleset applied org-wide (apply-org.sh) or per-repo (apply.sh) changed branch protection silently. Control-tested against real production data, not just synthetic fixtures: gh api repos/thrillmade/agent-skills/rulesets/<id> (read-only) shows all three org-level rulesets on that org, including org-staging which targets refs/heads/dev, already carry the bypass-defeats-deletion-restriction shape -- this is the live ruleset behind the 2026-08-14 dev-branch-deletion incident the check exists for.

**Alternatives considered:** Require all of RepositoryRole maintain(4)+admin(5)+OrganizationAdmin for bypass-defeats-deletion-restriction, matching the incident narrative's 'Repository admin, Maintain, Organization admin' -- rejected after pulling the real ruleset: GitHub does not publish a stable actor_id-to-role mapping beyond RepositoryRole admin=5 (corroborated by this repo's own README, cli/cli#13388, and the nskit Python client's RepositoryRole enum, which encodes only admin=5 for exactly this reason), and the live org-staging/org-baseline/org-default-protection rulesets on thrillmade/agent-skills all carry RepositoryRole actor_id=2, not 4 -- a hardcoded id=4 would never have fired on the incident it was written for, Hard-block admin-bypass-required in apply-org.sh only (zero disruption, org-baseline.json already conforms) and leave apply.sh unguarded or warn-only for it, since baseline/clud-bug/public-guard ship bypass_actors:[] by deliberate, documented design (README: 'OFF by default -- no built-in self-mod use case') -- rejected as inconsistent: same defect class, same validator, smaller blast radius is not zero blast radius, and the die message is fully actionable (--bypass-admin already exists), Leave the bypass-vs-intent check out of reporulez entirely since the actual incident ruleset wasn't applied by reporulez -- rejected once gh api confirmed the same defect exists on reporulez's own toolkit's applied rulesets on live repos (agent-skills' own reporulez-default ruleset, id 16434011, also carries OrganizationAdmin+RepositoryRole(5), diverging from the shipped skdd.json template), making it squarely in scope for the same tool that already audits live drift

**Implications:**
- Real behavior change: baseline/clud-bug/public-guard's default apply.sh invocation (no --bypass-admin) now dies with an actionable error instead of applying. skdd is unaffected (bypass_admin defaults on). apply-org.sh's only variant, org-baseline, already conforms -- zero disruption there
- SPEC section 6.6's second clause (the regenerating identity needs its own distinct bypass) is deliberately NOT checked -- requires per-repo knowledge (does a derived-doc regenerator run here) the ruleset JSON alone can't supply. Flagged, not silently dropped: see PR description
- audit.sh --include-ruleset now surfaces real, live drift: agent-skills' three org-level rulesets (org-baseline, org-default-protection, org-staging) and its repo-level reporulez-default ruleset all currently fail bypass-defeats-deletion-restriction on GitHub today -- read-only finding, not remediated by this change

## 2026-08-24 12:06 - reporulez PR #69 pass 2: bypass-defeats-deletion-restriction was refuting a false claim as a hard gate; downgrade to WARNING, fix the message, and revert org-baseline.json's admin-bypass swap

**Reasoning:** Deleting a branch requires only write access, not admin (GitHub docs + the delete-ref API's write-only permission requirement + allow_deletions' own field description), so an admin-only bypass on a deletion rule does NOT 'protect nobody' as the check's ERROR-severity message claimed -- it still restricts every real Write/Maintain-role holder. Independently confirmed on thrillmade/protocol: a live write-and-not-admin collaborator matched by none of that repo's four bypass entries. Worse, SPEC section 6.6 requires every ruleset carry an admin bypass, so every SPEC-6.6-conformant ruleset with a deletion rule necessarily has the exact shape this check flagged -- a hard gate that fires on every conformant input is not a gate. Reconciled: bypass-defeats-deletion-restriction is now WARNING severity (integration-id-pin and admin-bypass-required stay ERROR -- both are genuine SPEC violations or forgeable security gaps, not shapes SPEC requires). The message no longer claims the rule protects nobody; it states what's actually worth reconsidering -- OrganizationAdmin excuses every org owner unconditionally, a population nobody administers per-repository, and SPEC 6.6's self-repair rationale doesn't obviously reach restoring a deleted branch. Once the check stopped hard-failing, rulesets/org-baseline.json's prior swap from OrganizationAdmin to RepositoryRole admin (id=5) -- made ONLY to silence the ERROR -- had no justification left: OrganizationAdmin is the only bypass GitHub documents as provably covering every org owner on every repo including ones created after apply-org.sh runs, while RepositoryRole admin alone rests on this script's own uncited ASSUMPTION about assigned-vs-effective permission. Reverted.

**Alternatives considered:** Keep bypass-defeats-deletion-restriction at ERROR and just fix its message -- rejected: every SPEC-6.6-conformant ruleset with a deletion rule would still hard-fail, which is the actual defect, not just the wording. Redesign the check's trigger condition to fire on genuinely non-admin bypass actors (RepositoryRole ids other than 5, Team, Integration) instead of on OrganizationAdmin -- this is the reverted partial patch's approach (jq migration half-done, 2 tests red when attempted); not adopted here since the brief's settled facts only address the OrganizationAdmin claim and severity, and this redesign is a materially larger, unproven change -- filed as an open gap in the script's own header comment instead, not silently dropped. Keep org-baseline.json on RepositoryRole admin since it already passes the validator -- rejected: passing a check that no longer hard-fails is not the bar: an org-wide floor advertised as protecting repos 'created in the future' needs the bypass GitHub documents as provably complete, not the one this script's own comment calls an assumption.

**Implications:**
- apply-org.sh's default (org-baseline) now trips bypass-defeats-deletion-restriction as a WARNING on every run -- informational only, does not block apply.sh/apply-org.sh, and audit.sh --include-ruleset does not count it as drift (it only captures ERROR-severity, '✗'-prefixed lines into field_violations by design). An org owner with no explicit per-repo Admin role is once again covered by the org-wide floor's bypass, reversing the narrower-coverage tradeoff the prior swap introduced. The check still does not flag the incident's actual non-admin bypass shapes (an unrecognized RepositoryRole id, a Team, or an Integration entry) at any severity -- documented as a real, open gap in the script's own header comment, not fixed here; closing it needs GitHub to document those actor shapes' effective permission or a second incident to ground a narrower rule. AGENTS.md's variant taxonomy (four current variants + org-baseline) was also stale (still named the pre-#63 copilot/external pair) and is now corrected, independently discovered while reading the file for this change.
